Chapter 1: Professional Software Development & Ethics

The Core Pillars of Engineering and Professional Conduct

1.1 What is Software Engineering?

Software engineering is an engineering discipline that is concerned with all aspects of software production from the early stages of system specification through to maintaining the system after it has gone into use.

  • Engineering discipline: Using appropriate theories and methods to solve problems bearing in mind organizational and financial constraints. It is not just writing code; it involves applying scientific principles to software creation.
  • All aspects of production: This spans beyond programming to encompass project management, development of tools, methods, theories to support software production, UI design, and rigorous testing methodologies.

Types of Software Products

  • Generic products: Stand-alone systems that are produced by a development organization and sold on the open market to any customer who is able to buy them (e.g., MS Office, CAD software). The specification is owned by the software developer.
  • Customized (Bespoke) products: Software that is commissioned by a specific customer to meet their own needs (e.g., air traffic control systems, customized hospital patient management systems). The specification is owned by the customer.

1.2 Essential Attributes of Good Software

Software must deliver the required functionality and performance to the user, but functionality alone is insufficient. The software must possess four critical attributes:

Software Quality Attributes

1. Maintainability: Software must be written in such a way that it can evolve to meet the changing needs of customers. Because the business environment is continuously shifting, software change is inevitable. Maintainable code is clean, modular, and well-documented.

2. Dependability and Security: This includes a range of characteristics spanning reliability, security, and safety. Dependable software should not cause physical or economic damage in the event of system failure. Malicious users should not be able to access or damage the system.

3. Efficiency: Software should not make wasteful use of system resources such as memory and processor cycles. Efficiency includes responsiveness, processing time, memory utilization, and physical hardware wear and tear in embedded systems.

4. Acceptability: Software must be acceptable to the type of users for which it is designed. This means that it must be understandable, highly usable, and technically compatible with other systems they use daily.

1.3 Software Engineering Ethics

Software engineering involves wider responsibilities than simply the application of technical skills. Engineers must behave in an honest and ethically responsible way if they are to be respected as professionals. Ethical issues are not strictly bounded by laws.

Specific Ethical Dilemmas

  • Confidentiality: Engineers must normally respect the confidentiality of their employers or clients irrespective of whether or not a formal confidentiality agreement has been signed.
  • Competence: Engineers should not intentionally misrepresent their level of competence. They should not knowingly accept work which is fundamentally outside their skillset.
  • Intellectual Property Rights: Engineers must ensure that client and employer IP is protected. This includes understanding the constraints of open-source licenses and avoiding plagiarism.
  • Computer Misuse: Software engineers should not use their technical skills to misuse other people's computers (e.g., playing games on employer machines, disseminating viruses, or unauthorized snooping).

ACM/IEEE Code of Ethics (The 8 Principles)

The IEEE Computer Society and ACM published a code of ethics outlining eight key areas of responsibility:

  1. Public: Act consistently with the public interest (e.g., whistleblowing on dangerous systems).
  2. Client and Employer: Act in a manner that is in the best interests of their client and employer consistent with the public interest.
  3. Product: Ensure that their products and related modifications meet the highest professional standards possible.
  4. Judgment: Maintain integrity and independence in their professional judgment.
  5. Management: Engineering managers and leaders shall subscribe to and promote an ethical approach to the management of software development.
  6. Profession: Advance the integrity and reputation of the profession.
  7. Colleagues: Be fair to and supportive of their colleagues.
  8. Self: Participate in lifelong learning regarding the practice of their profession.

Chapter 2: Software Processes and Models

Structured Engineering Workflows

2.1 Core Software Process Activities

A software process is a structured sequence of activities required to develop a software system. While different projects organize these differently, all processes share four fundamental activities:

  • Software Specification: The functionality of the software and constraints on its operation must be defined.
  • Software Design and Implementation: The software to meet the specification must be structured, modeled, and subsequently programmed.
  • Software Validation: The software must be comprehensively tested to ensure that it does what the customer actually wants.
  • Software Evolution: The software must evolve to meet changing customer, market, or regulatory needs.

2.2 Process Models

A software process model is an abstract representation of a process. It presents a description of a process from some particular perspective.

1. The Waterfall Model (Plan-Driven)

A plan-driven model where phases are distinct and strictly sequential. You do not move to the next phase until the previous one is fully complete, documented, and signed off.

  • Phases: Requirements Analysis → System/Software Design → Implementation & Unit Testing → Integration & System Testing → Operation & Maintenance.
  • Advantages: Simple to manage, provides clear milestones, generates extensive documentation. It is appropriate when requirements are perfectly understood and fixed upfront (e.g., hardware-interfacing systems).
  • Disadvantages: Highly inflexible. It is extremely difficult and costly to respond to changing customer requirements. A working model is only seen very late in the project ("Big Bang" integration).

2. Incremental Development

Specification, design, and implementation are interleaved rather than sequential. The system is developed as a series of versions (increments), with each version adding specific functionality based on client priorities.

  • Advantages: The cost of accommodating changing requirements is drastically reduced. Customers get value early and can use the core functionality while other pieces are being built. Faster feedback loops.
  • Disadvantages: The process is not highly visible (managers need regular hard deliverables to measure progress). System structure tends to degrade as new increments are added ad-hoc unless significant time is spent refactoring the codebase.

3. Integration and Configuration (Reuse-oriented)

Based on widespread software reuse where systems are integrated from existing components or COTS (Commercial Off-The-Shelf) applications rather than built from scratch.

  • Process Sequence: Requirements specification → Software discovery and evaluation → Requirements refinement (adapting needs to fit available software) → Application system configuration → Component adaptation and integration.
  • Advantages: Significantly reduced costs and deployment risks. Much faster delivery timelines.
  • Disadvantages: Requirements compromises are inevitable; the final system may not meet the exact bespoke needs of users. There is a complete loss of control over the evolution of the reused third-party elements.

4. Boehm's Spiral Model

A risk-driven process model framework. The process is represented as a spiral rather than a sequence of activities with backtracking. Each loop in the spiral represents a phase in the process.

  • Objective Setting: Specific objectives for the phase are identified.
  • Risk Assessment and Reduction: Risks are assessed and activities put in place to reduce the key risks (e.g., building a prototype to mitigate UI risk).
  • Development and Validation: A development model for the system is chosen based on risk evaluation.
  • Planning: The project is reviewed and the next phase of the spiral is planned.

2.3 Coping with Change

Change adds costs, specifically the cost of rework. Software engineering uses specific approaches to reduce the cost of rework:

  1. System Prototyping: An initial version of a system used to demonstrate concepts and try out design options. It allows stakeholders to experiment with a working model to refine their requirements.
  2. Incremental Delivery: Deploying system increments to the customer for comment and actual operational use, rather than delivering a massive system all at once.

Chapter 3: Agile Software Development

Rapid Value Delivery and Adapting to Change

3.1 The Agile Philosophy

Agile methods were developed in the 1990s to reduce delivery time and to overcome the bureaucratic heavy weight of plan-driven models. They focus on the code rather than the design, iterative development, and delivering working software quickly to users.

The Agile Manifesto Core Values

1. Individuals and interactions over strict engineering processes and tools.

2. Working software over massive, comprehensive traditional documentation.

3. Customer collaboration over complex contract negotiations and rigid scopes.

4. Responding to change over strictly sticking to a pre-conceived project plan.

3.2 Extreme Programming (XP)

XP is a prominent, highly disciplined Agile methodology focusing intensely on technical excellence and engineering practices. It pushes recognized good practices to "extreme" levels.

  • Pair Programming: Two programmers sit at one workstation. One types (the Driver), one reviews the code and thinks strategically (the Observer). This leads to fewer bugs, continuous real-time code review, and shared domain knowledge across the team.
  • Test-Driven Development (TDD): Writing an automated unit test before writing the production code. The developer writes a failing test defining a new function, writes the minimal code to pass the test, and then refactors. This ensures 100% test coverage and acts as executable documentation.
  • Continuous Integration (CI): As soon as work on a task is complete, it is integrated into the whole system. All unit tests must pass upon integration, preventing the "integration hell" commonly found in Waterfall models.
  • Refactoring: Constantly cleaning up and improving the internal structure of the code without altering its external behavior to prevent code rot.

3.3 Scrum Framework

Scrum is an Agile management framework used to manage complex product development. It is an empirical process based on transparency, inspection, and adaptation.

Detailed Scrum Roles

  • Product Owner: Represents the business/customer. Solely responsible for maximizing the value of the product. They own the Product Backlog and must clearly prioritize its items.
  • Scrum Master: A servant-leader and facilitator. Removes impediments (blockers) for the team, protects the team from external interference, and ensures Scrum rules are understood and enacted.
  • Development Team: A self-organizing, cross-functional group of professionals who do the actual work of delivering a potentially releasable Increment of "Done" product at the end of each Sprint.

Detailed Scrum Events

  • The Sprint: A fixed timebox (usually 2-4 weeks) during which work is completed. Once a Sprint begins, its goals cannot be changed.
  • Daily Scrum: A 15-minute daily synchronization meeting for the Dev Team to inspect progress toward the Sprint Goal. (What did I do yesterday? What will I do today? Are there any blockers?)
  • Sprint Review: Held at the end of the Sprint to inspect the Increment and adapt the Product Backlog if needed. A collaborative demonstration, not a status report.
  • Sprint Retrospective: An internal team meeting to inspect how the last Sprint went regarding people, relationships, processes, and tools, aiming to identify improvements for the next Sprint.

3.4 Scaling Agile

While Agile works well for small, co-located teams building independent software, scaling it to large enterprises (e.g., systems of systems, teams of 500+ developers) presents challenges. Frameworks like SAFe (Scaled Agile Framework) and Spotify's "Tribes and Squads" model attempt to solve cross-team dependencies and architecture alignment.

Chapter 4: Requirements Engineering & Human Aspects

Elicitation, Analysis, and Team Dynamics

4.1 The Requirements Engineering Process

Requirements are descriptions of the services that a system should provide and the constraints on its operation. The overall RE process involves four high-level activities:

  1. Elicitation and Analysis: Discovering requirements by interacting with stakeholders (users, managers, domain experts).
  2. Specification: Converting these requirements into a standard, structured document format.
  3. Validation: Checking that the documented requirements actually define the system the customer wants.
  4. Management: Managing changes to the requirements as the system evolves.

4.2 Types of Requirements

  • User Requirements: High-level statements in natural language plus diagrams of the services the system provides and its operational constraints. Written for customers and non-technical management.
  • System Requirements: A highly structured document setting out detailed descriptions of the system's functions, services, and operational constraints. It defines exactly what should be implemented and often serves as a binding contract between client and contractor.

Functional vs. Non-Functional

  • Functional Requirements (FRs): State specifically what the system should do, how it reacts to particular inputs, and how it behaves in specific situations. (e.g., "The ATM system shall dispense cash immediately upon PIN verification and limit approval").
  • Non-Functional Requirements (NFRs): Constraints on the services or functions offered. They dictate *how* the system operates rather than *what* it does. They often apply to the system as a whole rather than individual features. If NFRs are not met, the system may be entirely useless even if all functional requirements are satisfied. Categories include:
    • Product requirements: Execution speed, response time, reliability (uptime %), security encryption standards, storage capacity.
    • Organizational requirements: Process standards that must be used, mandated implementation languages, delivery schedules.
    • External requirements: Interoperability with legacy systems, legislative/regulatory compliance (e.g., GDPR, POPIA), ethical constraints.

4.3 Requirements Elicitation Techniques

Gathering requirements is notoriously difficult because stakeholders often don't know what they want, express requirements in their own confusing domain terminology, and often change their minds midway through the process.

  • Interviews: Formal or informal discussions with stakeholders. Good for getting an overall understanding of business goals but poor for understanding complex, unstated domain-specific rules.
  • Ethnography: An observational technique. The requirements analyst immerses themselves in the working environment to observe day-to-day work. Excellent for discovering implicit requirements and workarounds that users utilize but don't think to mention in an interview.
  • Use Cases / Scenarios: Describing specific interactions between the users and the system to clarify how the system should respond under specific conditions.

4.4 Requirements Validation Checks

Checking that the requirements actually define the system that the customer really wants. Discovering a requirements error after the system has been built is the most expensive type of error to fix.

  • Validity Checks: Does the system provide the functions which best support the customer's needs?
  • Consistency Checks: Are there any conflicting requirements? (e.g., requiring a system to be accessible via simple text message but also requiring biometric facial recognition).
  • Completeness Checks: Are all functions required by the customer explicitly included?
  • Realism Checks: Can the requirements actually be implemented given the available budget and contemporary technology?
  • Verifiability: Is the requirement written in a way that can be realistically and mathematically tested? (e.g., "The system must be easy to use" is untestable. "An experienced user must be able to complete a transaction in under 3 mouse clicks" is testable).

4.5 Human Aspects (Pressman Supplement)

Software engineering is a highly human-centric activity. The success of a project is often determined more by team dynamics than by technical tooling.

  • Cognitive Factors: Software development requires intense, sustained cognitive load. Interruptions and toxic work environments severely degrade code quality.
  • Team Structures:
    • Democratic Decentralized (DD): No permanent leader, decisions made by consensus. Good for highly complex, novel problems requiring innovative research, but can be slow.
    • Controlled Centralized (CC): "Chief Programmer" model. Top-level problem solving by a senior engineer, internal coordination handled by a project manager. Good for straightforward, well-understood tasks.
  • Team Cohesion: Productive teams rely on individual responsibility, deep attention to detail, mutual trust among members, and high resilience under pressure. "Jelled" teams exhibit significantly higher productivity and lower turnover.

Chapter 5: System Requirements Modeling

Graphical UML Visualizations

5.1 What is System Modeling?

System modeling is the process of developing abstract models of a system, with each model presenting a different view or perspective. We almost universally use the Unified Modeling Language (UML) to establish a common visual vocabulary among engineers.

The 4 Core Architectural Perspectives

1. Context Models: Show how the target system fits into its broader environment alongside other external boundaries and interacting systems. They establish what lies inside and outside the system scope.

2. Interaction Models: Show dynamic interactions between the system and external actors, or between the internal components of the system itself.

3. Structural Models: Show the static organization of system data, objects, and components.

4. Behavioral Models: Show dynamic execution patterns in response to data changes or external events.

5.2 Key UML Diagrams in Detail

1. Use Case Diagrams (Interaction Perspective)

Used to represent the functional interactions between external actors (users or other systems) and the system itself. They define the functional scope of the project.

  • Actors: Represented by stick figures. An actor is a role played by an external entity (e.g., "Customer", "Bank Admin System").
  • Use Cases: Represented by ovals containing text. They define discrete, valuable tasks (e.g., "Withdraw Cash", "Reset Password").
  • System Boundary: A large rectangle enclosing the use cases, indicating what is inside the system vs. the actors outside.
  • Includes Relationship: A mandatory dependency where one use case requires another to function (e.g., "Withdraw Cash" <<includes>> "Verify PIN").
  • Extends Relationship: An optional variation or specific condition path (e.g., "Deposit Funds" <<extends>> "Print Receipt").

2. Sequence Diagrams (Interaction Perspective)

Models the chronological interactions between the actors and the objects within a system for a specific use case scenario.

  • Lifelines: Vertical dashed lines dropping down from an object at the top, showing the existence of that object over time.
  • Messages: Horizontal arrows passing between lifelines. A solid arrow indicates a synchronous call (the sender waits for a response). A dashed arrow indicates an asynchronous message or a return value.
  • Activation / Execution Occurrences: Thin vertical rectangles placed on lifelines showing exactly when an object is actively processing data or executing a method.

3. Class Diagrams (Structural Perspective)

Shows the object classes in the system and the associations between these classes. This is the foundational diagram for Object-Oriented design and database mapping.

  • Classes: Represented by rectangles divided into three horizontal compartments: Top (Class Name), Middle (Attributes/Variables), Bottom (Operations/Methods).
  • Visibility Identifiers: + (Public), - (Private), # (Protected).
  • Multiplicity: Defines how many instances of one class can be associated with another (e.g., 1..* means one to many; 0..1 means zero or one).
  • Inheritance (Generalization): A solid line with a hollow, un-filled arrow pointing to a superclass. Indicates an "is-a" relationship.
  • Aggregation / Composition: Represented by a diamond on the line. Aggregation (hollow diamond) implies a "has-a" relationship where the child can exist independently. Composition (filled diamond) implies strict ownership where the child dies if the parent is destroyed.

4. State Machine Diagrams (Behavioral Perspective)

Shows how individual objects change state in response to specific events over time. Essential for real-time, embedded, or highly reactive systems.

  • States: Rounded rectangles representing conditions during an object's life (e.g., "Waiting for PIN", "Dispensing Cash").
  • Transitions: Solid arrows connecting states, labeled with the specific event that triggers the change.
  • Entry/Exit Actions: Activities that automatically occur the moment a state is entered or exited.
  • Guard Conditions: Boolean expressions enclosed in brackets [ ] that must evaluate to true for a transition to occur.

5. Activity Diagrams (Behavioral Perspective)

Similar to flowcharts, they show the flow of control or object flow from activity to activity. Excellent for modeling complex business processes or algorithms.

  • Activities: Rounded rectangles representing a step in the process.
  • Decision Nodes: Diamond shapes where the flow diverges based on conditions.
  • Forks and Joins: Thick black horizontal lines representing the splitting of flow into concurrent, parallel threads (fork), or the merging of parallel threads back into one (join).
  • Swimlanes: Vertical columns that divide activities based on who or what is responsible for performing them (e.g., "Customer Lane", "System Backend Lane").

Chapter 6: Architectural Design

High-Level Structural Blueprint Patterns

6.1 The Role of Architecture

Architectural design is the first stage in the software design process. It represents the critical link between requirements specification and detailed implementation processes. It involves identifying the major structural components in a system, their core responsibilities, and the communication relationships between them.

Architecture and System Characteristics

The chosen architecture directly impacts the non-functional properties of the system:

  • Performance: Architectures that localize critical operations and minimize subsystem communications perform faster.
  • Security: Architectures that use a layered approach with critical assets in the innermost layers improve security.
  • Safety: Architectures that isolate safety-critical components from the rest of the system reduce risk.
  • Availability: Architectures utilizing redundant components and fault-tolerant failovers ensure high uptime.
  • Maintainability: Architectures utilizing fine-grained, self-contained components are easier to change without breaking other parts.

6.2 Architectural Views (Krutchen's 4+1 View Model)

Software architecture cannot be documented in a single diagram. It requires multiple perspectives:

  • Logical View: Shows the key abstractions in the system as objects or object classes (focus on functionality).
  • Process View: Shows how, at run-time, the system is composed of interacting processes (focus on performance and availability).
  • Development View: Shows how the software is decomposed for development into modules or packages (focus on code organization for programmers).
  • Physical View: Shows the hardware infrastructure and how software components are distributed across physical processors or cloud servers.
  • +1 (Use Cases): The scenarios that tie all the views together to prove the architecture works.

6.3 Core Architectural Patterns

Patterns are stylized descriptions of good design practice, which have been tried, tested, and formalized across thousands of successful projects.

1. Model-View-Controller (MVC)

Separates presentation and interaction from the core system data and business logic. It is the dominant pattern for web and application frameworks.

  • Model: Encapsulates the application data and the business rules that manipulate it. Completely blind to the user interface.
  • View: Handles rendering the data to the user interface. Multiple views can exist for the same model (e.g., a pie chart view and a spreadsheet view).
  • Controller: Manages user inputs (mouse clicks, HTTP requests), updates the model accordingly, and selects the appropriate view to display.

2. Layered Architecture

Organizes the system into a set of distinct, hierarchical layers. Each layer provides a specific set of services to the layer immediately above it and consumes services from the layer below it. Promotes extreme modularity and separation of concerns.

  • Example Stack: User Interface Layer → Application Logic Layer → Core Business Rules Layer → Data Access / Database Layer.
  • If you swap out an Oracle database for a MySQL database, only the Data Access layer needs to change; the UI and Business logic layers remain completely untouched.

3. Repository Pattern

All shared data in a system is managed in a central repository or database that is accessible to all system components. Components do not interact directly with each other; they only communicate through the central repository.

  • Best utilized in systems where massive amounts of data must be shared across disparate modules, such as IDEs (Integrated Development Environments) where the compiler, debugger, and code editor all interact with the same source code repository.

4. Client-Server Pattern

Functionality is organized into isolated services, with each service delivered from a separate server. Clients are instances of programs that require these services and access them across a network.

Modern Extension: Microservices

While Sommerville covers the foundational client-server pattern, modern cloud-native applications often break this down further into Microservices Architecture. Instead of a massive monolithic server handling all logic, the backend is split into dozens of small, independently deployable services (e.g., a dedicated "Payment Service", a separate "User Profile Service"). These are typically containerized (using Docker) and managed by orchestrators like Kubernetes, ensuring high availability, fault isolation, and independent scaling.

Chapter 7: Design, Implementation & Reuse

System Realization and Component Economies

7.1 Object-Oriented Design (OOD) Process

Developing an object-oriented system involves identifying object classes, their attributes, methods, and the relationships between them. A typical OOD process includes:

  1. Understand and define the context: Determine the system boundaries and define the specific modes of use via use cases.
  2. Design the system architecture: Select an overarching architectural pattern (e.g., MVC or Layered) to house the objects.
  3. Identify the principal system objects: Analyze the requirements document. Nouns often become Classes, while verbs become Methods/Operations.
  4. Develop design models: Create UML sequence diagrams and state machine diagrams to show the dynamic run-time behavior of how objects will pass messages to each other.
  5. Specify object interfaces: Precisely define the public methods (APIs) so objects can communicate, while hiding the internal implementation details (encapsulation).

Core Object-Oriented Principles

  • Encapsulation: Bundling data and the methods that operate on that data into a single unit (class), restricting direct access to some of the object's components.
  • Inheritance: A mechanism where a new class derives properties and characteristics from an existing class, promoting code reuse.
  • Polymorphism: The ability of different classes to be treated as instances of the same class through a common interface, allowing methods to execute differently based on the object calling them.

7.2 Software Reuse Economies

Modern software engineering is rarely about writing raw code from scratch. It is largely about discovering and securely assembling pre-existing, tested components to increase speed and reliability.

The Four Levels of Software Reuse

1. Abstraction Level: You do not reuse raw source code directly. Instead, you reuse successful overarching concepts and architectural design patterns (like utilizing the MVC pattern to structure your app).

2. Object Level: Directly reusing specific, compiled object classes from specialized runtime programming language libraries (e.g., importing a java.util.Scanner or a Python math module).

3. Component Level: Integrating larger collections of objects and classes that operate together as a framework to handle specific subsystems (e.g., embedding the Spring Boot framework or a React UI library).

4. System Level: Deploying entire, complex off-the-shelf COTS applications to fulfill broad corporate workflows (e.g., deploying Microsoft Exchange for email instead of building an email server, or integrating SAP for accounting).

7.3 Configuration Management

During implementation in a team environment, you must track code changes meticulously to prevent chaos. Configuration Management handles this through several pillars:

  • Version Management: Keeping track of multiple different versions of software components. It ensures developers do not overwrite each other's code when working simultaneously (e.g., using Git branches and pull requests).
  • System Building: The automated process of compiling the correct versions of components, linking them, and creating an executable program.
  • Release Management: Preparing software for external release and keeping track of the system versions that have been delivered for customer use.

CI/CD Pipeline Integration

In a modern DevOps workflow, Configuration Management acts as the automated trigger for a Continuous Integration / Continuous Deployment (CI/CD) pipeline. When a developer pushes a commit to a central Git repository, the pipeline automatically spins up, pulls the code, compiles it, runs automated unit test suites, and packages it into a deployment artifact. This completely automates the risky transition from Chapter 7 Implementation to operational deployment.

7.4 Open Source Development and Licensing

Open source implies that the source code of a software system is published and volunteers are invited to participate in the development process. However, open source is not legally "free to do whatever you want." It is governed by strict licenses:

  • GNU General Public License (GPL): A strict, reciprocal "copyleft" license. If you use GPL code within your proprietary application, you are legally forced to release your entire application's source code under the GPL as well.
  • GNU Lesser General Public License (LGPL): A compromise license. You can dynamically link to LGPL libraries within your proprietary, closed-source software without being forced to publish your own code.
  • MIT / BSD Licenses: Highly permissive. You can do almost anything with the code, including heavily modifying it and selling it in a closed-source proprietary product, as long as you maintain the original copyright notice in the documentation.

Example 1: Coding via Pair Programming & Continuous Integration
