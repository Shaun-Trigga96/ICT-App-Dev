2.1 Testing strategy for FinServe loan module? Levels: (1) Unit testing — test individual loan calculation functions. (2) Integration testing — test loan module with customer data and credit-check API. (3) System testing — end-to-end loan application workflow. (4) Acceptance testing — bank stakeholders verify against business requirements. Non-functional: Performance testing (response <3s under 1000 users); Security testing (data encryption, SQL injection); Reliability testing (24/7 uptime). [1.5 marks per testing level, 3 marks non-functional, 1.5 marks justification]
2.2 Two maintenance types for FinServe? (1) Adaptive maintenance — e.g. updating interest rate calculation logic when government regulations change the maximum lending rate. (2) Perfective maintenance — e.g. optimising the loan approval workflow to reduce processing time from 48 hours to 24 hours based on user feedback. Accept also: Corrective (fixing bugs in repayment schedule display) or Preventive (refactoring code before adding new loan products). [3 marks per type: 1 name, 1 definition, 1 specific example]
3.1 Four PM activities for smart parking project? Any four: (1) Planning — define scope, timeline, milestones, resource allocation. Important to set clear expectations. (2) Risk management — identify/mitigate risks early to avoid delays. (3) Scheduling — create Gantt chart; assign tasks to 8 developers; identify critical path. (4) Progress monitoring — weekly stand-ups, burndown charts to track velocity. (5) Stakeholder communication — regular status reports to keep client informed. (6) Budget management — track actual vs planned spend. [2.25 marks per activity: 1 description, 1.25 importance]
3.2 Risk mitigation strategies? (1) Key developer leaving: Mitigation — implement pair programming and knowledge sharing sessions; maintain up-to-date documentation; cross-train at least 2 developers on all critical modules; have a recruitment plan ready. (2) Uncertain API availability: Mitigation — build a mock API/stub early so development can continue without the real API; negotiate an SLA with the vendor; design the system with an abstraction layer so the API can be swapped. [3 marks each: 1 risk acknowledged, 2 specific mitigation steps]
