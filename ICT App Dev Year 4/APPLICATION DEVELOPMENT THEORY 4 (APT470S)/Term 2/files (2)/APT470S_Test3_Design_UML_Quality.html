Q# Question Model Answer

1.8 Easy to modify without introducing defects? c) Maintainability
1.9 High cohesion, low coupling desirable? TRUE
1.10 Sequence diagram shows static structure? FALSE — sequence diagrams show dynamic interactions over time; class diagrams show static structure
1.11 Measures independent paths through a program? b) Cyclomatic complexity
1.12 Refactoring definition? b) Restructuring existing code without changing its external behaviour
1.13 Black-box testing focuses on internal implementation? FALSE — black-box testing tests inputs/outputs without knowledge of internal implementation
1.14 Customer places Order — best UML diagram? b) Sequence diagram (shows the interaction/flow between Customer, Cart, and Order objects over time)
1.15 Example of a design pattern? b) Singleton
2.1 Monolithic vs Microservices for RetailPlus? Monolithic: simple to develop initially, single deployable unit, easier testing. Disadvantages: hard to scale individual components, slow to deploy changes, technology lock-in. Microservices: each service independently deployable/scalable (e.g. product service separate from payment). Disadvantages: complex orchestration, network latency, distributed system challenges. Recommendation: Microservices for RetailPlus as e-commerce platforms need independent scaling of catalogue, cart, payment. [3 marks each architecture, 3 marks recommendation with justification]
2.2 Activity Diagram for Place Order? Key activities: (1) Customer browses catalogue → (2) Adds item to cart → (3) Proceeds to checkout → (4) [Decision] Is user logged in? Yes → (5) Enters delivery details → (6) Selects payment method → (7) Confirms order → (8) System processes payment → [Decision] Payment approved? Yes → (9) Order confirmed, email sent. No → Error message. [1 mark per clearly described activity + decision point, up to 6 marks]
3.1 UML Class Diagram for Library Management System? Minimum 4 classes: Book (attributes: ISBN, title, author, available; methods: checkOut(), returnBook()), Member (attributes: memberID, name, email; methods: borrowBook(), returnBook()), Loan (attributes: loanID, loanDate, dueDate; methods: calculateFine()), Librarian (attributes: staffID; methods: addBook(), removeMember()). Relationships: Member borrows Book (many-to-many via Loan); Librarian manages Book. [1.5 marks per class with attributes+methods, 1.5 marks for correct relationships = 9 marks]
3.2 Two quality attributes for Library System? Any two: (1) Reliability — system must correctly track all loans without data loss. Measured by: running system under load and checking transaction accuracy; target <0.1% error rate. (2) Usability — librarians and members must find the system easy to use. Measured by: usability testing with real users; task completion rate target >90%. (3) Security — member data must be protected. Measured by: penetration testing; ensure data encrypted at rest. [3 marks each: 1 attribute name, 1 explanation, 1 measurement example]
