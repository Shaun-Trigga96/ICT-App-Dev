Q1
Recursion
Implement a recursive method for factorial
5 marks
⌄
📖 Explanation
✅ Model Answer
🧠 Test Yourself

What is recursion?

A recursive method is one that calls itself. Every recursive solution needs two things:
  • Base case — the condition that stops the recursion (prevents infinite loop)
  • Recursive case — where the method calls itself with a smaller input

Factorial defined

n! = n × (n-1) × (n-2) × … × 1, and 0! = 1 (by convention).

So 5! = 5 × 4 × 3 × 2 × 1 = 120
Recursive thinking: factorial(n) = n × factorial(n-1). You reduce the problem to a smaller version of itself. factorial(5) → 5 × factorial(4) → 5 × 4 × factorial(3) → ... → stops at factorial(0) = 1

5-mark answer structure

For 5 marks your answer needs: correct method signature (1), correct base case (1), correct recursive call (1), correct return (1), compiles/runs correctly (1). 
/**
 * Recursive Factorial
 * Time:  O(n)  — n recursive calls
 * Space: O(n)  — n stack frames held in memory simultaneously
 */
public static int factorialRecursive(int n) {
    // BASE CASE — stops the recursion
    if (n == 0) {
        return 1;
    }
    // RECURSIVE CASE — calls itself with smaller input
    else {
        return n * factorialRecursive(n - 1);
    }
}

Iterative = using a loop

Instead of calling itself, the iterative version uses a for loop to multiply numbers from 1 to n. No call stack growth — just a single method running to completion.
Key difference from recursion: Iteration is like driving to a destination with a GPS — you follow steps one-by-one in a loop. Recursion is like nesting dolls — each call contains another call inside.

What you need for 5 marks

Correct method signature, initialise prod = 1, loop from 1 to n (inclusive), multiply in each iteration, return prod. 
/**
 * Iterative Factorial
 * Time:  O(n)  — n loop iterations
 * Space: O(1)  — only 2 variables regardless of n (prod, i)
 */
public static int factorialIterative(int n) {
    int prod = 1;             // accumulator — start at 1 (not 0!)
    for (int i = 1; i <= n; i++) {  // n iterations
        prod = prod * i;
    }
    return prod;
}

Q3
Stack Frames · Big O
Using stack frames, explain the performance of the recursive method using Big O notation
10 marks — most important question
⌄
📖 Explanation
✅ Model Answer
🧠 Test Yourself

What is a stack frame?

Every time a method is called, the JVM allocates a stack frame — a block of memory on the call stack. It stores:
  • The method's local variables (n, in our case)
  • The return address (where to go back when done)
  • The return value placeholder
Analogy: Think of the call stack as a stack of trays in a cafeteria. Each call adds a tray on top. You can only remove the top tray. When a method returns, its tray is removed.

Why this matters for Big O

For factorial(n), each call creates a new stack frame. With n=5, you get 6 stack frames (5 down to 0) existing in memory at the same time before any return happens. This is the O(n) space complexity.

Time complexity

Each call does exactly 1 multiplication, and there are n calls. So time complexity = O(n).

Written answer (10 marks structure)

Time Complexity — O(n): For factorial(n), the method makes exactly n recursive calls (n → n-1 → n-2 → … → 0). Each call performs one multiplication. Total operations = n. Since we drop constants, this is O(n) — linear time.
Space Complexity — O(n): Each recursive call creates a stack frame stored in memory. At peak, all n+1 frames exist simultaneously (before any return). As n grows, so does memory usage proportionally. This is O(n) — linear space. This is the hidden cost of recursion.
Stack overflow risk: For very large n (e.g. n=10,000), the stack fills up and throws a StackOverflowError. Iterative factorial has no such risk because only 2 variables live in memory regardless of n — O(1) space.
What is the space complexity of recursive factorial(n) and why?
○ O(1) — because it only uses one variable
○ O(n²) — because recursion multiplies the calls
○ O(n) — because n stack frames exist simultaneously in memory
○ O(log n) — because each call halves n
Q4
Comparison · Real World
Compare recursive vs iterative: time & space utilisation. Which is preferable in the real world?
5 marks
⌄
📖 Explanation
✅ Model Answer
🧠 Test Yourself

Same time, different space

Both recursive and iterative factorial are O(n) time — both do n multiplications. The difference is space:
  • Iterative: O(1) space — only variables prod and i, fixed amount
  • Recursive: O(n) space — n stack frames in memory simultaneously
Overhead cost of recursion: Each stack frame doesn't just hold variables — the JVM must also manage return addresses, which adds extra overhead compared to a simple loop variable increment.

Real-world preference

For factorial specifically: iterative is preferred because it's more memory-efficient. However, recursion is preferred for problems that are naturally recursive — like tree traversals, where the iterative version would require you to manually manage your own stack.

Big O Analysis
Determine the Big O expression for each of the three code excerpts
3 + 3 + 3 = 9 marks
⌄
📖 How to Analyse
✅ All Three Answers
🧠 Test Yourself

The 4-step method for any code excerpt

  • Step 1: Identify what n is (the input size)
  • Step 2: Count how many times the inner-most statement executes as a function of n
  • Step 3: Drop constants and lower-order terms
  • Step 4: Express as O(?)
Key rules:
• Single loop that runs n times → O(n)
• Two separate loops (not nested) → O(n) + O(n) = O(2n) = O(n)
• Nested loop (both run n times) → O(n × n) = O(n²)
• Inner loop that multiplies/divides (j=j*3, j=j/2) → O(log n) for that loop
• Nested: outer O(n) + inner O(log n) → O(n log n)

Excerpt A — Two sequential loops

int sum = 0;
for (int i = 0; i < n; i++) {
    sum = sum + a[i];         // runs n times
}
for (int j = 0; j < n; j++) {
    sum = sum + a[j];         // runs n times
}
Analysis: Two separate (sequential, not nested) loops each run n times. Total = n + n = 2n operations. Drop the constant 2 → O(n)

Excerpt B — Nested loop with logarithmic inner

int prod = 1;
for (int i = 1; i < n; i++) {          // outer: runs n times
    for (int j = 1; j < n; j = j * 3) { // inner: j triples each time → log₃(n)
        prod = prod * j;
    }
}
Analysis: Outer loop runs n times. Inner loop: j = 1, 3, 9, 27, ... — it triples each iteration so it runs log₃(n) times. Nested = n × log₃(n) → O(n log n)

Excerpt C — Nested loop with step-3 outer

int sum = 0;
for (i=0; i<=n-1; i+=3) {        // outer: i=0,3,6,9... → n/3 iterations
    for (j=n-1; j>0; j--) {         // inner: j goes from n-1 down to 1 → n iterations
        sum = sum + (i * j);
    }
}
Analysis: Outer loop: i increments by 3, so runs n/3 times (still O(n) after dropping constant). Inner loop: j goes from n-1 down to 0, runs n times. Nested: O(n/3) × O(n) = O(n²/3) → drop constant → O(n²)
A loop where j = j * 2 each iteration (j starts at 1, goes to n) — what is its Big O?
○ O(n)
○ O(log n)
○ O(n²)
○ O(2n)

The mechanism

Bubble sort compares adjacent pairs and swaps them if they're in the wrong order. The largest unsorted element "bubbles up" to its correct position after each pass.
  • Pass 1: Largest element guaranteed to end up at index n-1
  • Pass 2: Second largest at index n-2, etc.
  • Each pass makes n-1 comparisons (or fewer as sorted tail grows)
For 12 marks: You need to show at least 2 full passes with all comparisons and clearly mark each swap. Show which elements are being compared at each step.

Best case (already sorted): O(n) with optimised version
Average and Worst case: O(n²) — (n-1) passes × (n-1) comparisons

📖 How Quick Sort Works
✅ Full Trace + Cases

The Quick Sort mechanism

Quick Sort uses a divide and conquer strategy:
  • Step 1 — Choose a pivot (here: always the middle element)
  • Step 2 — Partition: move elements < pivot to the left, elements > pivot to the right
  • Step 3 — Recurse: apply Quick Sort to the left and right sub-arrays
  • Step 4 — Combine: the sub-arrays are already in place — no merging needed
Key insight: After partitioning, the pivot is in its final correct position. It never moves again. Everything to its left is smaller, everything to its right is larger.

Middle element pivot

For array of size n, middle index = floor(n/2).

Performance — Best / Average / Worst Case (6 marks)

CaseTimeWhen?Why?
Best O(n log n) Pivot always splits array in half log n levels of recursion × n work per level
Average O(n log n) Random/typical input Expected balanced-enough partitions
Worst O(n²) Pivot is always min or max One side always empty — degrades to n levels × n work
Worst case happens when: array is already sorted and you always pick first or last as pivot — each partition only removes 1 element. This is why choosing a random or median pivot matters in production.
Space complexity: O(log n) on average (recursion stack depth). O(n) worst case.
When does Quick Sort perform at its worst — O(n²)?
○ When the input is completely random
○ When the array has an odd number of elements
○ When the pivot is always the smallest or largest element, causing unbalanced partitions
○ When there are duplicate elements
